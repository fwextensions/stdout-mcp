stdout-mcp

stdout MCP Architecture

How console output gets from your extension to a coding agent, what the tap, the stdout extension and the daemon say to each other, and why the agent talks stdio to a relay instead of HTTP to the daemon.

The pieces

Green lines are HTTP to the daemon, black lines are local message passing. Every relay talks to the same daemon, so all sessions see the same logs.

PieceHow manyLifetimeJob
Tap One per page or worker of your extension While that page or worker runs The code that runs in your extension once it calls stdout(). It sends each console call to the stdout extension and still logs it locally. The tap in your service worker also reloads your extension when asked.
stdout extension One in Chrome While Chrome runs Stores console calls from every tap, even when agent mode is off. In agent mode, sends them to the daemon as they arrive, checks in every 30 seconds, and runs the daemon's commands.
Daemon One per machine Until 2 hours idle, or replaced Holds the logs, accepts them from the extension, and runs the MCP tools. It's the only process the extension talks to.
Relay One per agent session The agent session Starts or replaces the daemon when needed, then copies MCP messages between the agent's stdio and the daemon's /mcp endpoint.

The two links

Each conversation between pieces has one module that owns it. That module defines every message, so both sides import the same definitions instead of each keeping its own copy. Both modules live in extension/, because an unpacked extension can't import anything outside its own folder. The tap and the daemon import them from there.

Tap Link

The tap and the stdout extension talk through chrome.runtime.sendMessage, which only carries JSON. It's defined in extension/tap-link.js. The stdout extension answers false to anything it doesn't recognize, and stores or registers nothing from it.

MessageSent byWhen and why
register Tap When stdout() is first called on each page or worker. The stdout extension remembers the extension, because agents can only reload extensions that have registered. It includes worker: true when it comes from a service worker. A reload counts that as proof the worker restarted, so a popup that reopens can't be mistaken for one.
log Tap On every console call. It carries the method, the arguments, the time, the page's filename, the extension's name and a load ID that changes each time the page or worker starts. Values that JSON can't carry, like a Map or an Error, are replaced with value tags. The stdout extension stores the entry and echoes it in its own console.
reload stdout extension When an agent asks to reload with the manifest. Only the tap in a service worker listens for this. It answers true, then calls chrome.runtime.reload(), and does that only once however many times it's asked.

Daemon Link

The stdout extension and the daemon talk over HTTP. Every request comes from the stdout extension, because the daemon can't start a conversation with it. It's defined in extension/daemon-link.js. Each /ingest request includes a linkVersion, which lets the daemon tell agents when the stdout extension in Chrome doesn't match it.

RequestWhat it carries
POST /ingest Up to 500 entries from the stdout extension's buffer, starting after the sync position, which is the last entry the stdout extension thinks the daemon has. The daemon answers with the position it really has, so the stdout extension can tell what to resend. A check-in sends the same request even when there are no new entries. An entry too big to send is replaced with a note, so it can't hold up the entries after it.
POST /commands Held open for up to 25 seconds, then answers with any commands that are queued, such as a reload.
POST /commands/result The result of a command, or why it couldn't run.

What happens on a tool call

  1. The agent calls a tool such as get_logs. It writes the JSON-RPC request to the relay's stdin.
  2. On the session's first message, the relay checks GET /health. If nothing answers, it starts the daemon as a detached process. If the daemon reports a hash of older code, the relay stops it and starts a new one.
  3. The relay sends the message to POST /mcp. If the connection fails because the daemon exited, it starts the daemon and sends the message again.
  4. The daemon creates an MCP server for this one request, runs the tool against its log store, and returns the result.
  5. The relay writes the response to its stdout, where the agent reads it.

Separately, the stdout extension posts to /ingest whenever new logs arrive and every 30 seconds, or every 5 seconds for three minutes after agent mode is turned on or Chrome starts. That's what turns its MCP badge green. It never talks to a relay.

The daemon can't start a conversation with the extension, so commands like reload_extension wait in a queue. While the daemon is running and agent mode is on, the stdout extension's service worker holds a POST /commands request open for up to 25 seconds at a time. That keeps only its own worker awake, and it stops when the daemon exits.

What happens on a reload

A reload uses both links.

  1. The agent calls reload_extension. The daemon queues the command and waits for its result.
  2. The stdout extension's open POST /commands request returns the command. The stdout extension checks that the extension is unpacked, turned on, and has registered.
  3. With reloadManifest, the stdout extension sends reload to the extension's tap. That wakes a sleeping service worker. If the worker hasn't called stdout() by the time the message arrives, the stdout extension asks again once the worker registers.
  4. The tap calls chrome.runtime.reload(), which reads manifest.json again. When the new worker's tap sends register with worker: true, the result is "reloaded". If the worker doesn't come back within 10 seconds, the result is "unconfirmed".
  5. Without reloadManifest, or if no tap answers, the stdout extension turns the extension off and on. That runs its code again from disk but keeps the manifest Chrome already read.
  6. The stdout extension posts the result to /commands/result. The daemon returns it to the agent with a cursor, so the agent can read only the logs from after the reload.

Why not put everything in the stdio process?

That would remove the daemon, but three things need a process that outlives any one agent session:

  • The stdout extension needs one fixed address. It posts to port 47321. Two agent sessions open at once would both try to listen on that port, and only one could.
  • Logs should survive the session. A process the agent starts also exits with it. A daemon keeps the logs for the next session, and the extension only resends what the daemon is missing.
  • Tool changes should reach every session. Because the tools run in the daemon, replacing it updates every open session at once.

Why not point the agent at the daemon's HTTP endpoint?

It would work while the daemon is running, since the relay only copies messages to the daemon's /mcp endpoint and back. What the relay adds is managing the daemon, which an HTTP URL in the agent's config can't do:

The extra hop is a local pipe plus one loopback HTTP request, so it adds only a few milliseconds to each call.

About "streamable"

Streamable HTTP is MCP's name for its HTTP transport. Each message is a POST, and the server can answer with plain JSON or, when it has several messages to send before the result (such as progress updates), with a stream of server-sent events. These tools don't send progress, so the daemon answers each request with a single JSON response. The relay gets that response and passes it straight to the agent.

With the 2026-07-28 protocol there are no sessions on the HTTP side either. Every request carries its own protocol version, so each one is handled by a fresh server. Clients still using the 2025 protocol are served the same way.

Using the HTTP endpoint directly anyway

If you'd rather skip the relay, start the daemon yourself and add it to Claude Code as an HTTP server:

node mcp/daemon.js
	claude mcp add --transport http stdout http://127.0.0.1:47321/mcp

The daemon accepts MCP requests that don't send a browser Origin header, which is how agents connect. You'd then have to restart the daemon after it exits for being idle, or raise STDOUT_MCP_IDLE_MINUTES, and restart it yourself after updating the package.

Every request must be addressed to 127.0.0.1:47321 or localhost:47321, which keeps web pages from reaching the daemon through DNS rebinding. Browsers always send an Origin with cross-origin requests, so web pages can't read the logs either.
